源码级结论（从 D:\DSHarness\resources\app.asar 解出 dsh 源码确认，非推断）：

1. 插件 prefix 路由不受鉴权保护。dsh-host-webserver 的 register(route) 只做路由登记，签名里没有 auth 参数（src/index.ts:445）；Host Connection 的鉴权只作用在它自己的 index / connect / API 载体上。因此 ctx.webServer.register({kind:'prefix'}) 注册的路由，任何本机请求都能直接 200。

2. DSH 的 web 鉴权模型：dsh web 打印的 URL 带一次性 ?token=<launchToken>。访问 / 时 authorizeIndex 校验该 token，通过则 303 铸签名 cookie，名为 dsh-auth-<base64url(sha256(authority))>，值形如 v<ver>.<body>.<HMAC-SHA256(secret)>，属性 HttpOnly; SameSite=Strict。此后每个请求靠该 cookie 验签。secret 是 32 字节，持久化在 credentials 里，key 为 client-connection/browser-session（browser-auth.ts:14,244-305）。唯一 401 文案 "dsh web authentication required; reopen the URL printed by dsh web." 出自 browser-auth.ts:385。

3. 复用方式：credentialKey(scope,id) 运行时返回字符串 "<scope>/<id>"（credentials-index.ts:75），CredentialProvider.readRecord(key) 是公开只读 API。所以第三方插件无需 import 任何内部包，就能取到同一 secret 并自行验签 cookie。

4. 不相关：ctx.authorization 是"需要人类交互获取凭据"的 OAuth 流接缝，与 HTTP 请求鉴权无关。

据此，pseudo-agi-panel 已改为自验该 cookie（单测 14/14），取代 mem-20261122-9d61328e 中"是否契约仍未决"的说法。
